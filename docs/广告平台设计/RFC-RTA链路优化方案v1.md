# RTA 链路优化方案 v1

状态：Proposed。2026-09-09。基于当前 V132/V133 工作树设计；本文件是优化方案，不代表以下优化已经实现或验收。执行基线为 ADR-017、ADR-018 与对应协议契约。目标是在保持正常业务结果及接口兼容的前提下，修复多策略异常隔离并降低请求处理开销。

## 1. 业务基线与验收口径

必须保留三条链路：

1. OPPO → SCX 策略映射 → 微风 RTA → SCX 同步返回允许策略。OPPO 不进入通用媒体异步通知队列。
2. 通用媒体 → SCX 202 受理 → 上游 GENERIC_ASYNC 或 WEIFENG_RTA → SCX 异步通知媒体。通用提交重试与通知签收规则保持原契约。
3. OPPO 点击 → 校验 RTA 状态/媒体/任务/设备/有效期/配置版本 → 原 Feedback 事实、计费及微风点击转发 → 上游 Callback → 原转化事实、去重和扣量 → OPPO 上传。

正常输入在相同配置、相同上游结果和足够时间预算下，优化前后的允许策略集合、供应商计划映射、上游请求次数、点击与转化事实、扣费、扣量结果必须一致。允许修正的差异仅限本文定义的异常分支：策略级配置失效不再拖垮其他有效策略；排队或超时任务更早停止无效工作。不能把所有策略一律拒绝视为“安全且验收通过”。

具体不变项：

- 媒体仍是下游账户；监测任务仍关联稳定 Integer 策略 ID 和上游接入。保留 aid/did 校验及原四实体主键，无新账户或策略主表。
- 所有现有 URL、签名算法、字段、返回结构、owner_id 配置语义、管理权限、设备处理规则保持兼容。OPPO 总时限保留现有配置，不擅自改变为合作方未确认的值。
- 24 小时请求幂等身份和内容冲突规则保持；微风结果不明时不自动重发。不能为提高成功率绕过 DISPATCH_ONCE。
- 已过决策截止时间不能恢复 ALLOW，已过准入有效期不能放行点击，配置停用或改绑仍触发门禁拒绝。
- RTA 本身不产生点击、转化或账务。原 Callback 事件映射、去重、计费、扣量与回传顺序保持。
- Redis 状态仍为真相，日志及报表继续由 XXL-JOB 落库；监控异常不得同步回退写 MySQL 或改变决策。

## 2. 第一版优化范围

### A. 多策略结果汇总一致性

涉及 OppoRtaService、RelayStore、state.lua。

当前汇总循环逐个执行 current() 和 SYNC_RESPONSE。若 A 已标记、B 配置变更抛异常，整批请求会失败，A 却已标记进入同步响应。改为“收集候选 → 分别校验 → 最终批量提交 → 组装响应”：

- 将可确定的策略失效（任务停用、改绑、计划不符）记录为该策略失败，从允许集合剔除，继续处理其他策略。
- 签名失败、请求身份冲突等仍按请求整体拒绝；Redis/MySQL 基础设施失败不冒充某个策略的业务拒绝，也不能使用未校验的旧结果。
- 校验阶段不标记 SYNC_RETURNED。最终通过一个有界 Lua 批操作，重新核对候选的 ALLOW、有效期、媒体和请求归属，再将仍有效的实际允许集合标记为现有 SYNC_RETURNED。由 Lua 返回实际集合，Java 不返回被过滤的策略。
- Lua 在写入前完成所有参数/状态解码和校验，避免脚本运行时错误造成部分写入；最多100条，不在脚本中遍历无界键集合。保留已有 key、状态字符串和 TTL，操作需幂等，不重复记决策计数。
- 数据库最终校验后仍可能出现并发配置变更，点击入口继续实时执行版本门禁；不能以批量提交替代点击门禁。
- SYNC_RETURNED 只表示选入响应路径，不能保证对方已收到网络响应。连接断开不撤回已经完成的上游决策，不重复询量；日志区分结果就绪、响应路径完成及超时，不能宣称媒体签收。

验收：A允许/B停用返回A；A拒绝/B允许返回B；全拒绝仍为正常空集合；全部基础设施失败不允许；准备期间状态过期被剔除；批量提交失败无正常成功响应；重试不增加微风派发次数。

### B. 完整超时预算与并发公平性

涉及 OppoRtaController、OppoRtaService、RelayWorker、RelayProperties。

- 增加内部 RequestBudget，入口记录截止时间并贯穿排队、路由查询、轮询、DNS、HTTP及结果提交。在每个可中断边界检查剩余时间；JVM 内等待使用单调时钟，Redis 持久化继续使用既有毫秒时间戳。
- 请求体读取、数据库和 Redis I/O 分别设置可执行的超时上界，区分合作方业务预算与基础设施硬超时。Servlet 定时器并不能中止同步 SQL；不能只新增一个 Deadline 类就宣称端到端时限已保证。
- 响应发送预留时间由基线测试确定，在既有总时限内分配。无法满足的预算及时结束等待，不延长原请求截止时间。已完成决策保留；尚未派发且过期的任务不再发送；已发送但结果不明的微风请求不重发。
- 使用可配置的有界响应等待线程、询量额度和通知额度。send/notify 保留各自最低并发机会，轮流领取，避免通知积压耗尽询量机会，也不能让询量淹没通知。
- 初始总出站并发预算以当前16为基线，具体配额依据两种协议混合负载测试确定；不通过无条件翻倍线程绕过容量限制。现有50ms调度周期先保留。
- 超时或客户端断开后，清理当前响应等待资源；Redis 状态及后台终态恢复继续由 Worker 管理。取消一个等待者不能破坏同一请求的另一个重试等待者。
- 新配置直写 profile YAML，使用兼容默认值；配置变更重新打包后生效。

验收：排队过期不发送；慢 SQL/Redis/上游不会无界占用线程；迟到结果不放行；一个媒体的通知重试不会饿死询量；双实例竞争与重启后仍遵循既有恢复/不重复派发规则。

### C. 批量查询与请求内配置复用

涉及 RelayRepository、RelaySqlMapper 及 XML、RelayService。

- 按媒体和策略集合一次批量解析任务、绑定、接入，沿用既有启用/归属过滤。共享上游与链接在同一次校验阶段仅查询一次。
- 将不可变 RouteSnapshot 显式传递给受理校验，减少 OppoRtaService 与 RelayService 的重复读取；保留普通入口的原方法及校验能力。
- 每个安全边界重新读取当前配置：受理、实际派发、同步结果汇总、点击门禁。各边界内部可批量复用，不把受理时快照直接当成点击时的最新配置。
- 第一版不引入跨请求本地/Redis配置缓存，避免新增缓存失效通道与停用延迟。仅当实测SQL仍占主要耗时，另行设计版本化缓存。
- 无已证实的索引瓶颈前不新增 DDL；使用隔离 MySQL 8.x 的 EXPLAIN 和实际 SQL 次数验证批量查询。

验收：混入其他媒体策略不能取得其任务；停用、改绑、aid/did变更在各门禁被拒绝；单策略没有额外SQL膨胀，多策略减少往返且不绕过实时检查。

### D. Redis 批量状态读取

涉及 RelayStore、OppoRtaService。

- 新增 getMany，按本次仍未完成的 relayRequestId 批量 MGET，按ID映射返回，避免逐策略逐条GET。
- 第一步保留现有轮询节奏和阻塞模型，仅替换读取方式，便于对照验证。轮询前后检查预算，已完成状态不再反复读。
- 单个状态不存在时定位到其策略并按约定处理；整次Redis调用失败视为基础设施故障，不使用默认ALLOW或静默吞异常。
- 保持现有同槽 key 布局及 JSON 状态格式。大批量时记录字节量和解码开销，限制每次最多100条。
- CompletableFuture、跨实例通知、Pub/Sub/Stream唤醒留待第二版；本版不增加可能丢唤醒的新业务依赖。

验收：1/10/100策略允许集合一致，乱序结果对应正确；相同轮询次数下网络往返由逐条读取变成一次批量读取；已完成状态、缺失状态及Redis中断都有明确行为。

### E. 受控的 HTTP 连接复用

涉及 RelayHttpTransport；媒体转化上传虽然复用了该类，也必须单独回归。

- 复用有界客户端/连接池，使用每次调用独立的剩余时限、请求头和签名，禁止共享可变凭据上下文。
- 每次出站继续执行HTTPS、允许域名、公网IP和路径/参数校验；已校验地址须与实际连接一致。客户端隔离键包含规范化目标主机、有效地址集合和安全策略版本，保留域名作为TLS主机名，不改用裸IP URL。
- 白名单撤销、地址集合或安全策略变化时，旧池不得为新请求服务；淘汰有上限、生命周期受控。首版关闭跨主机HTTP/2连接合并，避免绕过地址隔离。
- 继续禁止代理、重定向和隐式网络重试。任何恢复动作都不能导致微风未知结果的二次派发。保留响应体限长和严格UTF-8解码。
- RTA询量与OPPO转化上传分开管理池/调用预算，保留上传固定接口和现有5秒预算、签名及业务ret校验。
- 保留短连接模式配置作为性能优化回退路径；连接复用只有在DNS变更、私网解析、白名单撤销、超时及跨凭据用例通过后才启用。

验收：同目标正常请求可复用连接；不同凭据不串头；复用期间撤销域名或解析到私网必须拒绝；HTTP异常不额外重发；OPPO上传签名仍按实际发送body计算。

## 3. 实施切片与证据

按顺序实施，每片完成后再进入下一片：

1. 建立回归/性能基线并增加观测：不修改业务判定，记录端到端、排队、配置读取、Redis、DNS/建连、上游耗时与超时阶段。
2. 完成A并通过状态一致性测试，再完成B并通过混合负载和超时测试。正确性修复作为新基线，不设置恢复已知缺陷的业务开关。
3. 完成C、D，每项分别与新基线对照，保留独立撤销代码变更的能力。
4. 完成E，初始短连接，隔离测试后再单独启用连接复用。

所有指标采用受控维度，例如协议、阶段、稳定原因码；不把请求ID、OAID、URL、密钥作为指标标签。指标包含P50/P95/P99耗时、允许/拒绝/错误/超时分布、排队长度、在途数、拒绝次数、SQL次数、Redis往返、连接复用情况及日志积压。指标缺失/失败不得改变业务返回。

## 4. 必须通过的回归与容量验证

功能回归：

- OPPO：单策略、多策略、全拒绝、部分成功、策略不存在、错误签名、owner_id两种约定、OAID缺失、同请求内容冲突。
- 时序：结果乱序、重复请求并发、超时前后竞态、最后校验期间配置变化、Redis写入失败、等待者断开、进程重启。
- 通用异步：202受理、上游提前回调、重复/冲突回调、安全重试、媒体通知失败重试、通知到期、事件门禁。
- 业务闭环：同一点击和转化重复到达，事实与扣费不重复；扣量比例不变；验证0%、100%和混合比例的确定性序列；OPPO实际收到预期事件/包名/请求ID/创意ID。
- 安全：媒体隔离、绑定/上游停用、私网DNS、重定向、凭据隔离、原设备和秘密不进入日志/浏览器、回调上下文仍可解密。
- 兼容：旧新版本混部读取同一批Redis状态；旧版受理由新版完成、新版受理由旧版恢复；发布和回滚都保留在途状态、TTL及XXL-JOB日志/统计。

容量验证使用相同隔离环境、固定模拟上游响应与数据集，分别测试1/10/100策略和10/50/100并发，再按已知业务峰值扩展。该矩阵是测试条件，不是承诺支持的生产容量。设置正常、慢响应、超时、通知积压、配置频繁变更五类场景；先预热再至少重复三轮。

建议验收门槛：正常确定性样例的允许集合及业务事实差异为0；重复微风派发、越权放行、过期放行、重复扣费为0；无故障场景不得增加业务错误/超时。相同负载下吞吐不降低、P95/P99无可重复的回退；超过基线5%的持续延迟回退作为停止灰度信号，最终阈值根据基线波动确定。SQL/Redis往返须实际减少，不能仅因提前拒绝请求而获得更低耗时。

代码门禁使用仓库的 backend-test、ocpx-engine-test、前端类型/静态/单测、契约及SQL边界检查。基础设施测试只使用隔离 MySQL 8.x 和 Redis；既有 MySQL 9.6.0 验证不能替代目标版本。新增连接池测试覆盖上报回传消费者。真实OPPO/微风时限、签名和宏仍需合作方UAT确认。

## 5. 灰度、回滚与范围限制

第一版不更改SQL表结构、外部API、Redis命名空间、已有状态字段和回调加密格式；新Lua操作仅使用旧版能读取的现有终态字段。兼容性必须用混部测试证明。

灰度按媒体或稳定请求身份路由，同一逻辑请求固定到同一版本；禁止把同一真实请求同时发送给两套实现，以免增加询量、点击或计费。比对仅使用模拟上游或已捕获且脱敏的结果，不能影子重放真实副作用。

每阶段先隔离回归，再小流量UAT，最后逐步放量并覆盖正常与高峰场景。任一业务差异、重复派发/扣费、越权或过期放行立即停止灰度；性能异常先退回对应性能优化，保留已验收的正确性修复。

保留每阶段JAR、配置和Git提交。实例退出先停止接收新请求、等待有界在途调用结束；结果不明的微风请求保留既有不重发标记。原子换包/重启时不删除Redis键、不重置队列、不清空幂等状态，也不执行数据库回退。单实例重启可能有短暂不可用，不能承诺零中断；需要零中断时先具备已验证的双实例排空切换能力。

本方案不扩展其他媒体/上游、不增加转化事件、付费金额或补偿队列。OPPO转化失败自动补发属于另一项业务交付，不能把本次RTA性能优化描述成已补齐回传可靠性。现有生产部署和真实合作方联调仍未完成。

## 6. 代码落点

- 决策汇总与等待：`scx-ocpx-engine/.../oppo/OppoRtaService.java`、`OppoRtaController.java`。
- 状态批操作：`scx-ocpx-engine/.../rta/relay/RelayStore.java`、`src/main/resources/rta/state.lua`。
- 配置批查：`RelayRepository.java`、`RelayService.java`、`RelaySqlMapper.java` 及其XML。
- 并发与运输：`RelayWorker.java`、`RelayHttpTransport.java`、`RelayProperties.java`、Engine profile。
- 观测与验证：`RelayTelemetry.java`、`RelayAudit.java`、`RelayIntegrationTest`、`OppoProtocolTest`，并补充完整点击—回调—账务/扣量回归。

实施时优先新增小而明确的内部方法/值对象。避免同时大规模改包、重命名全部状态或引入第二套媒体适配框架，确保每个差异都能与链路优化目标对应。
