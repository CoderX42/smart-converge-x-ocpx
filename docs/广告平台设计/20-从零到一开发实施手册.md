# 20 从零到一开发实施手册

- 文档状态：Active（技术基线以 ADR-0002 为准）
- 适用阶段：M0-M5；M6/M7 在对应 ADR 接受后继续扩展
- 目标读者：产品负责人、开发人员、测试人员及后续 Coding Agent
- 前提：这是全新工程，不继承任何旧项目代码、表、接口或配置

## 1. 开发目标

从空目录开始，逐步交付一套可真实运行、可核验、可持续迭代的广告平台。首个生产可用版本不是“页面齐全”，而是以下闭环成立：

`主体与权限 → 配置投放 → 生成追踪 → 接收展示/点击/转化 → 去重归因 → 媒体回传 → 计费记账 → 报表对账 → 运营处置`

M6 实时竞价和 M7 智能优化不进入第一条闭环。

## 2. 编码前必须关闭的决策

以下任一 P0 决策未关闭时，只能搭建与决策无关的工程基座，不能创建相应业务表或对外协议：

| 决策 | 输出 | 阻塞内容 |
| --- | --- | --- |
| 技术栈与仓库 | 接受 ADR-0002 | 工程骨架、依赖、部署。 |
| 首批媒体/广告主协议 | 新 ADR/RFC + test vectors | 事件字段、追踪令牌、回传适配器。 |
| 财务计费口径 | 账务 ADR | 金额表、扣费、账单、对账。 |
| 隐私与保留 | 合规 ADR | PII 字段、日志、归档和删除。 |
| 容量输入 | SLO/容量评审 | 分区、缓存、集群、压测基线。 |

## 3. 推荐实现基线（ADR-0002 已接受）

为了让一人公司和 Agent 协作保持低运维成本，推荐从“模块化单体 + 独立事件入口/Worker”开始：

| 层级 | 推荐基线 | 理由 |
| --- | --- | --- |
| 管理后端 | Java + Spring Boot | 领域、事务、迁移和生态成熟。 |
| 管理前端 | TypeScript + Vue 3 | 已接受，不再保留 React 分支。 |
| OLTP | MySQL 8.x | 已接受，不再保留 PostgreSQL 分支。 |
| 缓存 | Redis | 幂等热键、限流、预算计数和缓存。 |
| 消息 | Apache RocketMQ | 已接受；事件重放、分区、消费扩展。 |
| OLAP | Apache Druid | 已接受；M4 报表接入，M0-M3 保留接口。 |
| 对象存储 | 阿里云 OSS（S3 兼容） | 已接受；素材、原始事件归档、导出和对账文件。 |
| 契约 | OpenAPI + AsyncAPI/JSON Schema | 让 Agent 和 CI 有机器可校验的事实源。 |
| 可观测性 | OpenTelemetry + Prometheus | 统一 trace、指标和日志关联。 |

如果最终选择其他技术栈，必须保持本文的模块、契约、数据所有权和质量门，不得因框架变化改变业务不变量。

## 5. 从空仓库启动 M0

### 5.1 第一步：接受决策

完成 Backlog `SCX-M0-001` 至 `SCX-M0-004`。将 ADR 状态从 Proposed 改为 Accepted 必须记录确认人和日期。代理商若未确认，首版明确延期，避免为不存在的商业关系预建复杂资金模型。

### 5.2 第二步：建立仓库护栏

创建以下根级文件或等价能力：

- `README.md`：项目目标、快速开始、文档入口。
- `AGENTS.md`：要求 Agent 阅读的基线、禁止事项和验证规则。
- `.editorconfig`、格式化/静态检查配置。
- `.env.example`：只含变量名和安全示例，不含真实密钥。
- 依赖锁文件、许可证策略、秘密扫描和漏洞扫描。
- CI：编译、lint、单测、契约校验、迁移校验、镜像构建。

### 5.3 第三步：本地依赖

提供一条命令启动数据库、Redis、RocketMQ、对象存储模拟和可观测性最小栈。必须健康检查、固定镜像版本、独立 volume 和清理说明。根目录目前提供如下统一入口：

```text
make bootstrap       # 首次安装/检查依赖
make dev-up          # 启动本地基础设施与应用
make dev-down        # 停止但保留数据
make dev-reset       # 明确确认后重建本地数据
make backend-test
make frontend-check
make contract-check
make db-verify
```

缺失的命令必须在 M0 结束前补齐，不能只保留文档。

### 5.4 第四步：最小可运行应用

先只实现：版本信息、liveness、readiness、数据库/缓存连通性、request_id/trace_id、统一错误响应和结构化脱敏日志。当前已提供 Actuator 健康端点与 `X-Request-Id`；完整 trace 导出和消息 trace 仍是 M0 待办。完成这些后才进入已确认的首条业务表迁移。

### 5.5 M0 完成条件

- 新机器按文档 30 分钟内启动。
- 空数据库可迁移，重复检查不破坏数据。
- OpenAPI、AsyncAPI 和 JSON Schema 校验进入 CI。
- 组件测试使用真实容器依赖，而非全部 Mock。
- 监控可看到一个 HTTP 请求和一条消息的 trace。
- 不存在源码密钥和生产数据。

## 6. 纵向切片开发方法

每次实现一个从页面/API 到数据、事件、测试和文档的完整小闭环。禁止先生成所有 Controller、所有表或所有空页面。

### 6.1 标准切片顺序

1. 在 Backlog 选择一个“已就绪”任务。
2. 补齐需求 ID、业务规则、权限和 Given/When/Then 验收。
3. 需要时先写 RFC/ADR。
4. 更新 OpenAPI/事件 Schema 和示例。
5. 设计领域模型、事务边界、数据库迁移和索引。
6. 先写关键规则/契约测试，再实现应用和基础设施。
7. 接入权限、审计、指标、日志和错误码。
8. 完成 UI 或调用方集成。
9. 运行单测、组件、契约、E2E 和受影响非功能测试。
10. 更新追踪矩阵、交接、风险和当前状态，提交验收。

### 6.2 第一条推荐切片：广告主只读闭环

目的：验证 IAM、主体归属、数据库、API、前端、审计和测试骨架。当前实现了广告主体只读、菜单权限和数据访问范围，审计与 E2E 仍待补齐。

交付：创建两个测试广告主 → 不同用户分别绑定主体 → 列表/详情 API → 控制台展示 → 非所属主体返回 404/403 → 审计访问 → E2E 证明无法越权。

暂不包含充值、投放或媒体，避免第一条切片同时引入财务和事件复杂度。

### 6.3 第二条推荐切片：活动草稿

创建活动草稿，使用整数预算、币种、时区和乐观锁；实现列表、详情、修改、版本冲突和审计。此时活动不能投放。

### 6.4 第三条推荐切片：创意审核

上传隔离素材 → 病毒/格式检查 → 创建创意版本 → 提交审核 → 通过/驳回 → 操作留痕。验证修改产生新版本而非覆盖已审核记录。

## 7. M1 身份与主体开发

### 7.1 实现顺序

1. 用户、密码哈希、会话和账户状态。
2. 角色、权限、资源归属和策略校验器。
3. 广告主、媒体主体与资质状态。
4. API Key 创建、一次显示、密钥引用、轮换和撤销。
5. 审计日志与高风险操作原因。

### 7.2 关键约束

- 身份验证和资源授权分开；登录成功不等于可以访问资源。
- 对不存在和不属于当前主体的资源避免泄露差异。
- 密码只保存强哈希；API Secret 只显示一次。
- 用户停用同时撤销会话和凭据。

### 7.3 验收

以两个广告主、两个媒体、平台运营和财务角色构造权限矩阵自动化测试。批量、导出、异步任务和缓存同样验证隔离。

## 8. M2 投放与库存开发

### 8.1 实现顺序

1. 媒体 → App/站点 → 广告位与格式。
2. 广告主 → 活动 → 计划 → 广告。
3. 素材 → 创意版本 → 落地页与审核。
4. 预算声明、排期、定向 DSL、频控策略。
5. 投放状态机、阻塞原因和操作审计。
6. 配置草稿、审核、发布、版本和回滚。
7. 媒体/广告位绑定与追踪令牌生成。

### 8.2 发布配置

发布时把投放层级、媒体绑定、价格/规则版本和追踪版本生成不可变快照，计算内容哈希。实时事件只能引用已发布且在事件发生时有效的版本。

### 8.3 定向设计

先实现明确的低基数维度：地域、设备系统、网络、媒体、广告位、时段和黑白名单。每个维度定义 operator、value schema、冲突优先级和可解释拒绝原因。首版不实现未经确认的人群画像。

## 9. M3 事件与归因开发

### 9.1 接入路径

事件网关只做快速且确定的工作：请求大小/类型、认证签名、时间戳/nonce、基本 schema、可靠保存和接收凭证。复杂归因、回传和报表异步处理。

### 9.2 可靠接收

- 先持久化原始事件或可靠写入消息，再返回 202。
- `source_scope + event_id` 建唯一约束。
- Outbox/Inbox 保证状态与消息一致。
- 坏消息隔离，不阻塞正常分区。

### 9.3 归因 Worker

按 `10-事件协议归因与回传.md` 实现：标准化 → 建触点 → 找候选 → 应用窗口/优先级 → 保存结果和原因 → 发布 attribution 事件。规则必须是可单测的纯逻辑，系统时间通过 Clock 注入。

### 9.4 回传 Worker

适配器实现统一接口：映射、签名、发送、响应分类和脱敏摘要。网络失败与业务失败分开；重试有上限；死信可审计重放。

### 9.5 黄金数据集

至少覆盖正常点击归因、展示兜底、重复事件、转化先到、乱序补齐、超窗、多个触点、错误签名、回传 429/5xx/4xx 和重放。

## 10. M4 数据与财务开发

### 10.1 计费事实先行

事件/归因模块只发布“满足规则的业务事实”，计费模块根据计费方式和价格版本生成唯一 billing_fact；账务模块只消费已确认 billing_fact。

### 10.2 账务实现

- 金额值对象包含 amount + currency，拒绝浮点。
- 流水只追加，业务幂等键唯一。
- 余额更新与流水同事务；每日用流水重算勾稽。
- 人工调整和冲正使用专用命令、分权审批和审计。

### 10.3 报表实现

先定义事实与指标，再写报表页面。流式结果为预估，日结为确认；报表携带口径版本。报表不作为资金余额来源。

### 10.4 对账

使用固定黄金账期验证 CPM/CPC/CPA、迟到事件、无效流量、冲正和舍入。对账文件解析失败不允许部分静默入账。

## 11. M5 风控与生产治理开发

先做可解释规则：高频 IP/设备、异常转化延迟、签名失败、同标识多账户和媒体突增。规则产生风险案件和证据，不直接删除事件；处置通过合法状态命令暂停、延迟确认或拦截。

完成 SLO、告警、Runbook、恢复演练、密钥轮换、数据修复 dry-run 和权限审计后才具备生产条件。

## 12. 前端开发规范

- 页面权限来自服务端能力，前端路由只改善体验，不能替代鉴权。
- API 类型优先从 OpenAPI 生成或校验，避免手写字段漂移。
- 通用组件：状态/原因、金额、时区、主体选择、审计抽屉、异步任务进度、危险操作确认。
- 报表明确实时/日结/重述状态、时区、币种、口径版本和最后更新时间。
- 表单处理服务端字段错误、版本冲突、防重复提交和离开未保存提示。
- E2E 使用角色和主体矩阵，不只测试管理员 happy path。

## 13. API 开发规范

1. 先更新 OpenAPI，再实现服务端与客户端。
2. Controller 只处理协议、认证上下文和 DTO；业务规则放应用/领域层。
3. 写接口使用幂等键；编辑使用乐观锁；状态迁移使用命令接口。
4. 错误码稳定、可观测，不把异常堆栈返回客户端。
5. 列表查询限制分页、排序和筛选白名单；大导出异步执行。
6. 每个资源 API 显式校验主体归属。

## 14. 数据库开发规范

- 迁移先于 ORM 代码合并；表和索引由所属模块维护。
- 约束尽量下沉：非空、唯一、检查约束、合法关联。
- 高频查询在设计时记录 SQL 形态和索引依据。
- 原始事件、流水、账单、审计不可物理删除或通用软删除。
- JSON 字段必须有 schema/version 和查询边界，不能成为逃避建模的万能容器。
- 测试覆盖空库安装、从上一版本升级、重复执行和前向修复。

## 15. 消息开发规范

- 消息采用标准信封和明确 schemaVersion。
- 生产使用 Outbox；消费使用 Inbox/幂等表或同等保证。
- Topic 记录生产者、消费者、分区键、顺序范围、保留期、DLQ 和 PII 等级。
- Consumer 先兼容新消息，再升级 Producer。
- 重试不能无限；毒消息隔离并告警。
- 重放前选择影子/隔离/正式模式，正式模式保持业务幂等。

## 16. 日志、指标和审计开发规范

每条入口请求至少包含 request_id、trace_id、版本、调用方和结果分类。业务日志记录 ID 和原因码，不记录密钥、完整令牌、手机号、设备明文或完整回调 payload。

每个纵向切片同步提供：成功/失败计数、延迟、队列积压/重试（如适用）、业务结果指标、错误告警和审计动作。

## 17. 自动化测试要求

| 变更 | 最低测试 |
| --- | --- |
| 纯规则 | 单元 + 属性/边界测试。 |
| 数据库 | 真实数据库组件测试 + 迁移测试。 |
| API | OpenAPI 校验 + 鉴权/主体隔离 + 幂等/冲突测试。 |
| 消息 | Schema/兼容 + 重复/乱序/重启测试。 |
| 外部适配器 | 固定 test vectors + 超时/限流/错误分类。 |
| 金额/预算 | 并发、重复、日切、冲正、溢出和勾稽。 |
| UI | 组件 + 关键角色 E2E。 |

测试报告必须记录提交、环境、命令、时间和报告路径。“本地测试通过”不是可接受证据。

## 18. CI/CD 流水线

### Pull Request

格式/静态检查 → 单元测试 → 契约语法/兼容 → 数据库迁移 → 组件测试 → 密钥/依赖/SAST → 构建。

### 主分支

全量集成/E2E → 镜像与 SBOM → 漏洞扫描 → 签名产物 → 部署测试环境 → 冒烟。

### 生产候选

预生产迁移 → 性能/安全/恢复验证 → 发布清单 → 人工审批 → 金丝雀 → 技术/业务/数据/财务校验 → 扩大流量或回滚。

## 19. Agent 开发协议

每个 Agent 开始前必须：读取 README、00、06、20、当前状态、任务相关规范与 Accepted ADR；检查工作区；声明目标/不做/影响/验证。

执行中：只处理一个纵向切片；保护他人修改；遇到计费、归因、权限、公开协议、生产数据或破坏性迁移先停下确认。

结束时：运行真实验证；更新契约、迁移、追踪矩阵、Backlog 和独立 handoff；列出限制和回滚。Agent 不得自行宣告高风险任务或里程碑已验收。

## 20. Definition of Done

任务只有同时满足以下条件才完成：

- 需求与异常路径已实现，未扩展未授权范围。
- 权限、主体隔离、幂等、并发和补偿已处理。
- API/消息/数据迁移与实现一致且向后兼容。
- 自动化测试、静态检查、安全检查和必要性能测试通过。
- 日志、指标、告警、审计和运维方式已提供。
- 回滚或前向修复路径可执行。
- 文档、追踪矩阵、Backlog 和交接已同步。
- 指定验收人依据可复现证据确认。

## 21. 推荐首批开发任务

在 M0 决策关闭后，按以下顺序开始，不要并行铺开所有模块：
