# 19 数据库与数据契约迁移

## 1. 基本规则

- 所有迁移只追加，已执行文件不修改、不重排、不复用编号。
- 每个迁移有唯一编号、模块、描述、作者/Agent、兼容性、校验和和回滚说明。
- 应用启动不自动执行未经审批的生产迁移；生产由受控任务执行并留审计。
- 迁移失败优先前向修复；不得假定破坏性 down 脚本安全。

## 2. 兼容迁移流程

`Expand → Backfill → Dual Read/Write（如需）→ Verify → Switch → Contract`

1. Expand：增加可空字段、新表、新索引或新 schema，保持旧版本可运行。
2. Backfill：分批限速回填，保存游标、错误和统计。
3. Dual：必要时双写/双读，并监控差异。
4. Verify：对行数、唯一性、金额、哈希和抽样业务结果做校验。
5. Switch：切换读路径或生产者版本，可通过开关回退。
6. Contract：确认无旧版本后，后续发布再删除旧结构。

## 3. 数据库迁移模板

每次迁移说明包含：目标、所属上下文、DDL/DML、影响行数、锁风险、预计时长、磁盘增长、应用兼容版本、执行步骤、监控、验证 SQL、停止条件、前向修复和备份点。

## 4. 大表与在线变更

- 新增索引或字段先在生产规模副本验证锁和复制延迟。
- 回填使用稳定主键游标、小批次、限速和断点续传，禁止无界全表事务。
- 达到锁等待、复制延迟、错误率或资源阈值立即停止。
- 原始事件、流水和审计表不使用通用软删除迁移。

## 5. 消息/API契约迁移

- 先使消费者兼容新旧 schema，再发布新生产者，最后弃用旧字段。
- 新增可选字段兼容；字段删除、改类型、改含义必须新版本。
- Schema 兼容检查进入 CI；示例消息和契约测试随版本提交。
- API 破坏变更使用新主版本并提供双轨期和迁移指南。

## 6. 缓存与分析模型迁移

- Redis Key 含命名空间和版本；新旧版本双读/回填后切换，设置旧 Key 过期。
- OLAP 表先增加列/投影，再更新消费任务；历史重算写入新版本或分区，经校验后切换查询。
- 缓存和报表都不是账务事实源，迁移失败不得修改资金结果。

## 7. 状态与参考数据

枚举新增需确认旧客户端对未知值的行为。删除/合并状态必须映射历史数据并保留展示含义。计费、归因和风控规则以版本化记录发布，不通过直接 UPDATE 改写历史语义。

## 8. 验收与证据

迁移报告至少记录环境、开始/结束时间、迁移版本、行数、错误、校验结果、资源图、应用版本和操作者。涉及金额的迁移必须完成总额、分账户余额和抽样流水勾稽。
