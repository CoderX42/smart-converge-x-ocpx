# SCX OCPX 本地 JMeter 压测记录（2026-07-23）

## 结论

- 在隔离的本地 MySQL、Redis、RocketMQ 环境中，100、300、600 QPS 三档稳定阶段的 HTTP 202 受理数均与最终 MySQL 原始事件数、唯一事件数、处理完成数一致。
- 三档稳定阶段合计受理并完成 `56,696` 条，最终 Outbox 未发送数为 `0`，Redis 64 个 Feedback 分区的 pending、lag、DLQ 均为 `0`，本次测试未发现已受理事件丢失。
- 300 QPS 停压后约 `152` 秒才完成全链路排空；600 QPS 停压后约 `402` 秒才完成全链路排空。入口短时承压能力高于异步消费能力，不能据此认定系统可持续承载 300/600 QPS。
- 默认全局限流为 200 QPS。未覆盖该阈值时，300 QPS 阶段出现 `3,390` 个 HTTP 429；这是明确拒绝，不属于“已受理后丢数”。
- 当前存在冷启动迁移与管理端审计日志两个上线阻断项，修复并重新做目标环境验收前不建议上线。

## 测试环境

- Git commit：`b4d539fe9ff4`
- JMeter：5.6.3，非 GUI 模式
- Java：OpenJDK 21.0.11
- 应用：单实例，端口 19999，堆 1–2 GiB
- 中间件：隔离的新 MySQL、Redis、RocketMQ、WireMock 容器与新数据卷
- 数据：70% CLICK、30% ACTIVATE；每条使用唯一 runId/eventId/device
- 签名：OCPX v1.1 HMAC；凭证仅通过临时权限为 600 的本地属性文件注入，未写入压测计划或产物
- 稳定的 300/600 QPS 阶段仅在隔离进程中把 `rate-limit.global.max-qps` 临时提高到 1000；生产默认仍为 200

## 默认限流对照

默认 `rate-limit.global.max-qps=200` 下尝试 300 QPS：

- JMeter 已记录 10,189 次请求：HTTP 202 为 6,799，HTTP 429 为 3,390。
- 为及时诊断限流原因，该阶段被人工中止；有 1 个已发出的 HTTP 202 样本未刷新到 JTL，数据库最终记录 6,800 条。
- 因此该中止阶段不参与“不丢数”正式统计，仅用于证明默认 200 QPS 全局保护会拒绝超额请求。

## 上线阻断与风险

1. **冷启动迁移错误**：全新 Compose 数据库只自动挂载 V1–V31；`init-database.sh` 自动基线却识别到 V41，导致 V32–V41 被标记但未执行，数据库校验仅发现 55/59 张必需表。显式设置 `SCX_MIGRATION_BASELINE_VERSION=31` 后才正确应用 V32–V41 并通过校验。
2. **管理端审计日志 500**：创建渠道客户端时，审计日志把完整 Java 方法名写入 `sys_log.request_method`，触发 `Data too long for column 'request_method'`，使管理操作返回 HTTP 500。本次隔离库临时扩大字段后才创建测试凭证；源码和正式迁移未修改。
3. **持续吞吐不足**：300/600 QPS 均产生显著异步积压。最终不丢数不代表实时处理能力满足生产 SLA。
4. **默认容量边界**：生产默认全局上限 200 QPS。提高阈值前必须按实例数、消费吞吐、积压告警和降级策略做容量设计。
5. **验证边界**：这是单机、本地、短时测试，不是生产网络、真实媒体回调、故障切换或持续容量验收。
